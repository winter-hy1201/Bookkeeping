# 页面返回现场与滚动恢复规格

> 2026-08-09 经逐项访谈确认。本文是页面返回现场能力的产品边界、实现约束与验收依据。

## Problem Statement

档口经营者从可滚动的 A 页面进入 B 页面查看、编辑或新建数据后，返回 A 页面时可能被带回顶部，搜索、筛选、折叠或表单草稿也可能丢失。当前页面虽然通过导航栈保留，但返回时的本地数据刷新、条件渲染和滚动容器重建会破坏原来的操作上下文，迫使用户重新定位刚才处理的位置。

## Solution

为所有通过前进导航打开下级页面的可滚动父页面建立统一的“返回现场”能力。现场只保存在当前页面实例内：返回时先刷新需要更新的本地业务数据，再恢复搜索、筛选、表单草稿、折叠状态和滚动上下文；列表结构未变化时恢复原像素，发生移动或删除时按原条目或相邻条目恢复。页面卸载或冷启动后不延续旧现场。

## User Stories

1. 作为档口经营者，我希望从列表进入详情再返回时仍停留在原来的滚动区域，以便继续处理相邻记录。
2. 作为档口经营者，我希望返回列表后保留搜索词，以免重新输入客户或业务信息。
3. 作为档口经营者，我希望返回后保留当前日期和筛选条件，以免误操作其他日期的数据。
4. 作为档口经营者，我希望返回后保留当前分栏，以便继续查看当前、未来或历史数据。
5. 作为档口经营者，我希望返回后保留列表分组的折叠状态，以便页面结构和离开前一致。
6. 作为档口经营者，我希望从未提交表单进入下级页面再返回时保留已填写内容，以免重复录入。
7. 作为档口经营者，我希望返回后看到刷新过的本地业务数据，以便刚完成的新增、编辑或删除立即生效。
8. 作为档口经营者，我希望数据未改变时恢复精确的滚动像素，以便视线落点不发生变化。
9. 作为档口经营者，我希望刚编辑的条目发生排序移动后仍出现在原来的屏幕区域，以便确认修改结果。
10. 作为档口经营者，我希望刚删除的条目消失后定位到下一相邻条目，并在没有下一项时定位到上一相邻条目，以便继续浏览。
11. 作为档口经营者，我希望列表被清空后回到顶部并看到正确空态，以免停留在无内容的滚动位置。
12. 作为档口经营者，我希望连续进入 B、C 等多级页面后逐级返回时，每一级父页面都恢复各自现场。
13. 作为档口经营者，我希望使用 Android 返回键、页面左上角返回或程序化返回时得到一致结果。
14. 作为档口经营者，我希望 App 暂时进入后台但未被系统结束时，当前导航链的返回现场仍然有效。
15. 作为档口经营者，我不希望冷启动后恢复昨天的滚动位置，以免误以为自己仍在旧任务中。
16. 作为档口经营者，我不希望返回后自动重新打开键盘、弹窗、选择器或确认框，以免产生意外操作。
17. 作为档口经营者，我不希望半截拖拽、按钮执行态或加载锁在返回后继续，以免页面进入不可理解的状态。
18. 作为档口经营者，我希望返回刷新失败时仍保留原现场并得到明确错误提示，以免被无故带回顶部。
19. 作为档口经营者，我希望返回刷新期间不能操作旧数据，以免对已变化的数据重复操作。
20. 作为档口经营者，我希望订单列表原有的拖拽和边缘自动滚屏继续可用，不因返回恢复而发生抖动。
21. 作为档口经营者，我希望客户列表原有的字母索引继续可用，并且不会与返回滚动定位互相覆盖。
22. 作为档口经营者，我希望使用内部滚动容器和原生页面滚动的页面表现一致，以免不同业务入口返回行为不同。
23. 作为维护者，我希望新页面可以复用同一套返回现场接口，以免每个页面重新实现滚动缓存。
24. 作为维护者，我希望页面卸载时现场自动释放，以免全局缓存积累过期状态。

## Implementation Decisions

- “返回现场”只保证当前页面栈内的前进导航与返回导航；标签页切换、重加载、页面卸载和冷启动不承诺恢复。
- 快照由页面实例持有，共享 composable 只统一记录、刷新协调、恢复和清理逻辑；不使用全局状态仓库、模块级缓存、本地存储或 SQLite。
- 快照包含滚动像素、离开前条目顺序、交互条目、交互条目的视口偏移和相邻条目；搜索、筛选、分栏、折叠与表单草稿继续由页面自己的响应式状态持有。
- 列表条目顺序未变化时恢复原像素；顺序变化时依次尝试原条目、下一相邻条目、上一相邻条目，均不存在时回到顶部。
- 页面从下级页面返回后自行读取最新本地数据，不依赖下级页面发送“已修改”事件；数据渲染完成后再执行定位。
- 返回刷新期间保留滚动容器实例并阻止用户操作旧数据；刷新失败时保留原内容和快照，给出可读错误，不强制归零。
- 未提交表单不因返回刷新而被业务数据覆盖；表单只刷新必要的辅助数据，草稿字段保持原值。
- 不恢复键盘焦点、弹窗、选择器、提示、拖拽过程、按钮执行态、加载锁或其他瞬时 UI。
- 共享能力同时适配内部纵向滚动容器和原生页面滚动，不批量转换现有页面结构。
- 订单列表继续复用既有受控滚动值和拖拽自动滚屏；客户列表执行返回恢复前清除字母索引使用的目标，避免高优先级定位覆盖像素恢复。
- 所有现有可滚动且会打开下级页面的父页面纳入本次接入；未来新增同类页面沿用相同规则。
- 不新增第三方依赖，不改变数据库 schema、业务 API、金额计算、订单状态机或备份格式。

## Testing Decisions

- 自动化测试只断言外部可观察的定位决策，不断言 composable 内部 ref、生命周期调用次数或选择器查询步骤。
- 最高测试接缝是纯粹的返回目标解析器：输入离开前条目、返回后条目和交互条目，输出原像素、原条目、下一相邻项、上一相邻项或顶部。
- 解析器覆盖条目完全不变、条目移动、条目删除但下一项存在、仅上一项存在、列表清空和无交互条目等分支。
- 类型检查与 lint 覆盖 composable 接口、两类滚动适配和所有页面接入。
- H5 构建用于确认模板事件、生命周期导入、选择器和滚动 API 能正确编译。
- Android 真机回归覆盖客户列表字母索引、订单拖拽、原生页面滚动、系统返回键、多级返回、编辑后重排、删除后相邻定位、刷新失败和表单草稿保留。
- 既有 Node 测试、样式预处理检查和 H5 构建继续作为回归先例；原生滚动与触摸行为仍以 HBuilderX Android App 基座为最终依据。

## Out of Scope

- App 冷启动、页面卸载、重加载或跨会话的滚动恢复。
- 将页面现场写入 SQLite、本地存储、Pinia 持久化或备份文件。
- 恢复弹窗、键盘焦点、选择器、拖拽手势和执行中操作。
- 重做导航系统、引入自定义路由器或统一替换现有滚动容器。
- 新增第三方 UI、状态管理或导航依赖。
- 改变订单、客户、次卡、支出、菜单、模板、统计或备份的业务规则。

## Further Notes

- 内部滚动容器的目标定位优先级高于像素定位，恢复前必须清除页面已有的临时目标。
- 返回现场是页面导航体验，不是盒记业务领域术语，因此不进入领域词汇表。
- 规格完成后按同一范围直接实施；CLI 通过不代表 Android 原生滚动与触摸已经验收。
